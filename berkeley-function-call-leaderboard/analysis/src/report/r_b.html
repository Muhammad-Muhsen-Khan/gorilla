Part four

Analysis

Finding 1 · read this before quoting any number

The base model's 0.00 is a parser artifact, and we measured what it hides

Base scores 0.00 on non-live, live and multi-turn. But 399 of 400 simple_python outputs contain a well-formed {"name": …, "arguments": …} object with the right function and arguments. They score zero because 0 of 5,017 generations wrap it in the <tool_call> tags the parser requires.

So we re-scored the same generations with a lenient parser — no new inference, no new sampling, the model's choices untouched. It wraps every well-formed call object it finds and discards the degenerate repetition that follows (base never emits a stop token, so every generation runs to the 2,048-token cap). A fidelity check confirms the rewrite invents nothing: 45,826 extracted calls, zero whose function name is absent from the raw output.

And the 100.00% irrelevance detection collapses to 17.92% the moment its calls parse, which settles what that number was: pure artifact. Nothing parsed, so it "abstained" everywhere. Read the other way, teaching the model when not to call (17.92 → 74.67) is the single largest genuine gain the fine-tune produced.

Finding 1b

What the fine-tune actually taught: selection and parallelism, not calling

The lenient breakdown separates two abilities the strict score fused together. On simple calls — one function offered, fill its arguments — base is already at 65.67 against the fine-tune's 74.33 and instruct's 73.42. Barely a gap.

The gap is everywhere else: multiple 58.50 → 91.50 and parallel 47.50 → 92.00. Base can fill in a function it is handed; it cannot reliably pick the right one from a catalogue or emit several calls at once. That — plus abstention and the wrapper protocol — is what the corpus taught.

Finding 2 · the control question, answered

The fine-tune did not break multi-turn — it never added it

This was the open question from the failure analysis: did SFT remove an ability, or fail to install one? The lenient re-parse makes the control exact. Base with a working parser scores 1.38% on multi-turn; the best fine-tune scores 3.25% and epoch 1 scores 1.25% — below base. Ten epochs of tool-calling data moved multi-turn by essentially nothing. Meanwhile the official instruct model — same architecture, same 4B parameters — reaches 31.75% on the identical test.

The ability is plainly reachable at this scale. Our corpus does not teach it. Transcript-level evidence agrees: on the 625 turns that hit a tool error, the model issued any follow-up call only 16–20% of the time, and 38–51% of turns contain no tool call at all. It emits a plausible batch of calls, reads a precise error telling it what to fix, and explains the failure to the user instead of fixing it.

Finding 3

Reasoning traces cost capability rather than adding it

The no-reason run beats the reasoning run on every metric at every epoch — about 3 points of Overall, 2–4 points of non-live AST, and roughly double on memory. Twenty runs pointing the same direction is not noise.

One caveat on causality: the two corpora differ in supervised-token density as well as in content (36.6% vs 14.1%), so this compares two training recipes, not reasoning-versus-no-reasoning in isolation.

Finding 4

Epoch barely matters — so the checkpoint selection measured the wrong thing

No-reason non-live AST across ten epochs: 87.21 · 83.17 · 85.81 · 84.81 · 84.98 · 85.81 · 85.96 · 86.08 · 86.08 · 86.08. Essentially flat. Over that same span eval_loss nearly doubled (0.378 → 0.702) and training loss fell to 3.0e-4 with token accuracy 1.000 — textbook memorisation.

That memorisation cost almost nothing downstream. And epoch 1 — the checkpoint an eval-loss criterion discards early, before the curve's minimum — turns out to have the highest single-turn score of the twenty. One epoch is enough for single-turn tool calling; the remaining nine bought roughly one point of multi-turn and nothing else.

Part five

How to read these numbers

Three caveats, in the order they affect conclusions.

Caveat 1

Overall Acc is depressed by roughly 20 points for every model

web_search is absent and counts as 0 against 40% agentic weight. Within-table comparisons are exact; do not put these Overall figures next to the public leaderboard.

Caveat 2

Tool schemas reach the model in a shape it never trained on

BFCL serialises tool docs flat — {"name": …, "parameters": {"type": "dict"}} — while all 67,288 tool definitions in both training corpora used the OpenAI-wrapped form with "type": "object". We kept BFCL's rendering deliberately: it is what every official Qwen3 entry gets, so the numbers stay leaderboard-shaped. But it means single-turn scores may understate the models slightly.

Caveat 3

19 entries could not run at all

18 multi_turn_long_context entries exceeded the 32,768-token context limit (one request reached 36,155) and one crashed on a KeyError. That is a harness ceiling, not a model failure, and it caps that category at 91% of its entries for every model equally.

What follows

The corpus is the thing to change

Every result here points at the training data rather than the hyperparameters. Single-turn is solved at epoch 1 and does not improve with more training. Multi-turn is near zero at every epoch of both runs, while a same-size model that saw multi-turn data reaches 31.75%.

The concrete check is cheap: count how many conversations in the corpus have more than one assistant turn, and how many contain a tool response carrying an error that the next assistant turn has to act on. If the second number is near zero, that is the finding — and the fix is data, not epochs.

Two smaller follow-ups worth the GPU time: run the epoch-1 no-reason checkpoint as the headline model rather than an epoch-2 pick, and add web_search once a paid SerpAPI tier is in place so the Overall figures become leaderboard-comparable.
