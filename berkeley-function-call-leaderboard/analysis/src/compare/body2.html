Part four

Twenty conversations, rendered whole

Scores compress a conversation to one bit. These do not. Five multi-turn tasks were drawn at random — seeded, from a fixed shuffle across all four multi-turn categories: two from base, one each from miss_func, miss_param and long_context. Every task is then replayed for four models: the untrained Base, the official Instruct reference, and the best checkpoint from each SFT run — no-reason epoch 7 and reasoning epoch 3.

All four models saw the identical system prompt and the identical scripted user turns, so the tabs are directly comparable: switch between them and only the model's own behaviour changes. Each card opens with that shared system prompt and the starting API state, then the conversation — user turns, the assistant's reasoning trace where it emitted one, its tool calls, and the real values the API returned.

None of the twenty passed. That is the expected shape of a random draw here, not a selection: at their measured pass rates a clean sweep of five failures is the most likely outcome for Instruct (about 15% likely) and near-certain for the two fine-tunes, which pass roughly 1 multi-turn task in 40. Nothing was filtered — the draw is what it is, and the failure banner on each tab names the exact scoring verdict.

How to read a card

ElementWhat it is
System promptThe full # Tools block BFCL builds — every function schema serialised flat, then the <tool_call> protocol instruction. 19–28 KB per task. Identical across all four tabs.
Initial API stateThe world before turn 1: the filesystem tree, the account balances, the vehicle's fuel level. Ground truth is a state comparison against this object after the last turn.
Turn n → step kA turn is one scripted user message. Within it the model may take several steps, each a generation followed by the tool results it triggered. A turn ends when the model emits no call.
reasoning traceCollapsed by default. Present for Instruct and for the reasoning-run checkpoint; the no-reason checkpoint emits none by construction.
tool responseWhat the API actually returned — including its error strings. These are the moments that decide the task, and the ones the fine-tunes ignore.
handler_logThe harness narrating itself. Empty response from the model. Proceed to next turn. means the model answered in prose instead of calling anything, and the turn was closed out.

Part five

What the transcripts show

Reading 1 · open the Base tab first

The untrained model is not answering — it is writing the rest of the conversation

Base's transcripts are unmistakable. It produces a correct call object, then keeps going: it invents the user's next question, answers that too, invents another, and runs until the generator is cut off. The delimiters it emits between those imagined turns decode as the stray fø you can see in the text — a base model reaching for a chat token it was never trained to place.

The numbers behind that impression, across all 800 multi-turn tasks: 85.3% of Base's generations run to the 1,000-token cap, against 0.6% for the no-reason checkpoint and 6.3% for Instruct. And 0 of 3,336 contain a <tool_call> tag — the single fact behind Base's 0.00 across four categories, and the reason its re-parsed score is 58.67% rather than zero.

Read the step counts too. Instruct takes 8,060 generations to work through the same 800 tasks; the no-reason checkpoint takes 5,334, and Base only 3,336. Fewer steps is not efficiency here — it is turns ending early because nothing callable came out.

Reading 2

Prose is a hard stop, and both fine-tunes reach for it

The harness ends a turn the moment a generation contains no parseable call. So an assistant message that says "the file is not present in the current directory — verify its location" is not a partial step towards the answer; it is the end of the turn, and the next user message arrives against unchanged state. Across the suite, 38–51% of fine-tune turns contain no tool call at all.

The pattern is visible in every card: a plausible opening batch of calls, a precise error from the API, and then an explanation addressed to the user rather than a correction addressed to the tool.

Reading 3

The models do not recover from errors they can read

On the 625 turns across the suite that hit a tool error, the fine-tunes issued any follow-up call only 16–20% of the time. The errors are not cryptic — {"error": "mv: cannot move 'final_report.pdf': No such file or directory"} names the file and the reason. What is missing is the move that follows: cd into the directory that holds it. Across 200 filesystem tasks, cd was called 11 times.

Reading 4

Reasoning traces make the failure longer, not different

Open the same card on the reasoning tab and then the no-reason tab. The reasoning checkpoint deliberates at length, then emits the same call the other model emitted directly — or, more often, deliberates and emits nothing. The traces do not surface the missing cd; they narrate around the error and conclude with advice.

They do cost context. The reasoning checkpoint hit the served context window on 26 multi-turn entries against the no-reason checkpoint's 16; the untrained base, which emits no traces, hit it zero times. Instruct — verbose by design — hit it 25 times, including one of the five tasks below, where its transcript is a context-length error rather than a conversation.

Reading 5

Failing at the end state is not the same as failing at every call

Several cards carry the verdict multi_turn:instance_state_mismatch — the model made sensible calls throughout and still left the API in the wrong state. Multi-turn is graded on that final object, not on the calls, which is why a transcript can read well and score zero. It is also why the multi-turn column is not a gentler version of the non-live column: the two measure different things, and the fine-tunes are strong at one and absent at the other.

Part six

How to read these numbers

Three caveats, in the order they affect conclusions.

Caveat 1

Overall Acc is depressed by roughly 20 points for every model

web_search is absent and counts as 0 against 40% agentic weight. Comparisons within this page are exact; do not put these Overall figures next to the public leaderboard.

Caveat 2

Tool schemas reach the model in a shape it never trained on

BFCL serialises tool docs flat — {"name": …, "parameters": {"type": "dict"}} — while all 67,288 tool definitions in both training corpora used the OpenAI-wrapped form with "type": "object". You can see the flat form in any card's system prompt. We kept BFCL's rendering deliberately: it is what every official Qwen3 entry gets, so the numbers stay leaderboard-shaped. It means single-turn scores may understate both runs slightly — and it affects both equally, so the head-to-head is unaffected.

Caveat 3

19 entries could not run at all

18 multi_turn_long_context entries exceeded the context limit and one crashed on a KeyError. That is a harness ceiling, not a model failure, and it caps that category at 91% of its entries for every model equally. One of the five sampled tasks hits it on the Instruct tab.

What follows

The corpus is the thing to change

The head-to-head answers which recipe to keep — no-reason, at 58 of 60 cells — but the transcripts say that choice is worth about three points of Overall against a gap of ten times that. Single-turn is solved at epoch 1 of either run and does not improve with more training. Multi-turn is at the floor for both, at every epoch, while a same-size model that saw multi-turn data reaches 31.75%.

The concrete check is cheap: count how many conversations in the corpus have more than one assistant turn, and how many contain a tool response carrying an error that the next assistant turn has to act on. If the second number is near zero, that is the finding — and the fix is data, not epochs, and not reasoning traces.
