Part one

What BFCL v4 actually measures

The Berkeley Function Calling Leaderboard tests whether a model can pick the right function and fill its arguments correctly. Version 4 keeps the single-turn and multi-turn categories from v1–v3 and adds agentic ones on top, so running v4 gives the earlier signal too. We ran 20 of its 22 scored categories, 5,017 generated entries per model.

Category groupEntriesWhat it asks of the modelHow it is scored
Non-live simple / multiple / parallel1,150Pick one function, or several, or several at once, from a hand-written catalogueAST match
Live (user-contributed)2,251Same, but on real function schemas donated by users — messier, more realisticAST match
Irrelevance / relevance1,140Recognise when no offered function fits, and abstain — or when one doesAbstention correctness
Multi-turn (4 categories)800Hold a conversation against a live stateful API — a filesystem, a vehicle, a trading bot — across several user turns, including turns with a missing function or parameterFinal API state + response
Memory (kv / vector / rec-sum)465Read and write to a memory backend across a session and use what it storedFinal state
Web search (excluded)200Multi-hop search and page-reading via a live search APIAnswer match

The three scoring mechanisms differ in kind. AST match parses the emitted call and compares function name and arguments against accepted answers — it never executes anything. Multi-turn and memory are state-based: the benchmark runs the calls against a real Python object and compares the final state of that object to ground truth, so a conversation that reaches the right end state passes even by a different route, and one that gets every call right but leaves the state wrong fails. Part three shows exactly this happening.

The weighting is where the headline number comes from

BFCL v4's Overall Acc is not an average of categories. It is a fixed weighting that puts 70% of the score on multi-turn and agentic work:

10101030 · multi-turn40 · agentic
  • Non-live
  • Live
  • Irrelevance
Overall = 0.10·NonLive + 0.10·Live + 0.10·Irrelevance + 0.30·MultiTurn + 0.40·Agentic Agentic = mean(Memory, WebSearch)

We verified this against the published CSV: it reproduces every one of our 22 rows to the second decimal.

Our Overall Acc figures are not comparable to the public leaderboard. We skipped web_search — the SerpAPI key on hand is free-tier, 250 searches against a category of multi-hop tasks needing several searches each, across 22 models. A missing category is scored as 0, not dropped, so web search being absent halves the agentic term and costs every model up to 20 points of Overall.

Comparisons within this page remain exact — every model is missing the same category. Only the absolute Overall numbers are depressed.

Part two

The head-to-head

Two SFT runs over Qwen3-4B-Base on a ToolACE-derived corpus: one rendering assistant turns as bare tool calls (no-reason, 64 steps/epoch), one interleaving reasoning traces (reasoning, 86 steps/epoch). Ten epoch checkpoints each, all 5,017 entries, no partial evaluation. Served through vLLM 0.8.5 in prompting mode with Qwen3's own tool template, which renders byte-identically to the template the models were trained under.

Every cell is a percentage. The winner of each pair is shaded — blue where no-reason wins, orange where reasoning does. The point of the table is the colour, not the digits: it is blue almost everywhere.

Δ is reasoning minus no-reason, on the ten-epoch mean. Negative everywhere.

The single orange cell is epoch 2, non-live AST — 85.88 against 83.17. Epoch 1 multi-turn is an exact tie at 1.25. Every one of the other 58 cells goes to no-reason. Twenty independently trained checkpoints agreeing this consistently is not sampling noise.

One caveat on causality, which the table cannot settle: the two corpora differ in supervised-token density as well as in content — 36.6% of tokens supervised in the reasoning run against 14.1% in the no-reason run. This compares two training recipes, not reasoning-versus-no-reasoning in isolation.

Part three

Where both runs sit

The head-to-head only says which fine-tune is better. These five rows say whether either one matters. The base model appears twice — once as BFCL scored it, once re-scored from the same generations with a lenient parser that accepts a well-formed call object without the <tool_call> wrapper.

ModelOverallNon-LiveLiveIrrel.Multi-TurnMemory

Base's 0.00 is a parser artifact. 399 of 400 simple_python outputs contain a well-formed {"name": …, "arguments": …} object with the right function and arguments — but 0 of 5,017 generations wrap it in the tags the parser requires. Re-scored leniently, with no new inference and no new sampling, the untrained base calls functions at 58.67% non-live and 40.49% live. A fidelity check confirms the rewrite invents nothing: 45,826 extracted calls, zero whose function name is absent from the raw output.

So the real gain from fine-tuning on single-turn is +28.5 points, not +87. And base's 100.00% irrelevance detection collapses to 17.92% the moment its calls parse — it was never abstaining, nothing parsed. Read the other way, teaching the model when not to call (17.92 → 85.16 mean for no-reason) is the largest genuine gain either fine-tune produced.
