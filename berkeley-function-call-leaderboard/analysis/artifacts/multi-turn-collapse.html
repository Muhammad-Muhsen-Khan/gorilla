Multi-Turn Collapse

This checkpoint scores 83% on non-live single-turn function calling and 1.5% on multi-turn. That gap is too wide to be a difficulty curve. Reading the transcripts, the tool calls themselves are fine — what is missing is the loop around them. The 22-checkpoint suite has since settled why; see the closing section.

The diagnosis

Syntax is not the problem

Every tool call the model emitted parsed cleanly. BFCL logged Successfully decoded model response on essentially every step that contained a call, and the JSON inside <tool_call> was well-formed throughout. The model knows the format. Four behaviours account for the collapse instead.

Failure 1 · the decisive one

It does not act on tool errors

Across 625 turns that hit a tool error, the model issued any follow-up call in only 16–20% of them. The other ~80% it turns to the user and narrates the failure. The environment's errors are not cryptic — they state the fix outright: “All doors must be locked before starting the engine.”

Failure 2

It exits the turn to prose

38–51% of turns contain no tool call at all — just an explanation or a clarifying question. A turn ends the moment the model emits no call, so prose is a hard stop. Median turn length is 1–2 steps; almost nothing runs past 3.

Failure 3

It does not carry state across turns

In base_0, turn 3 re-issues turn 0's calls verbatim — including mkdir temp, which had already succeeded — and gets File exists back. Nothing from earlier turns informs later ones.

Failure 4

It asks instead of looking

Given “search the file for budget analysis”, it asks the user which file — in a session where the filename appeared one turn earlier and ls was on the tool list. It prefers a question to an inspection call.

Resolved · 22-checkpoint suite

The control came back: never added, not removed

This page originally ended on an open question — whether the fine-tune removed multi-turn ability or never installed it. We since ran all 22 checkpoints, and the answer is unambiguous.

ModelMulti-turnNon-liveWhat it settles
Base, lenient parse1.38%58.67%the untrained floor
SFT no-reason, epoch 11.25%87.21%below the floor
SFT no-reason, best of 10 epochs3.25%85.81%ten epochs bought ~2 points
Qwen3-4B Instruct, same size31.75%87.23%reachable at 4B

Nothing was removed — the base model was already at the floor. And nothing was added: ten epochs of tool-calling data moved multi-turn from 1.38% to at best 3.25%, while a same-architecture, same-parameter-count instruct model reaches 31.75% on the identical test. The ceiling is the corpus, not the model.

One correction to this page's framing. The 83% single-turn figure above was measured against a base model that appeared to score 0%. That 0 turned out to be a parser artifact: the base emits well-formed {"name": …, "arguments": …} objects but never the <tool_call> wrapper, so nothing parsed. Re-scoring the same generations leniently puts it at 58.67% non-live.

So the single-turn gain is real but far smaller than it looked — roughly +28 points, not +83. That makes the contrast on this page sharper rather than weaker: the fine-tune moved single-turn work by 28 points and multi-turn by essentially zero.

The remaining check is still the corpus one, and still cheap: how many toolace-tooling-sft conversations have more than one assistant turn, and how many contain a tool response carrying an error the next assistant turn must act on. Every behaviour catalogued on this page — the 16–20% error-recovery rate, prose as a hard stop, no state across turns, asking instead of looking — is what a model trained only on single exchanges would do.
