Headline

Epoch 2 wins, epoch 3 gives some back

Overall accuracy peaks at the second epoch and declines at the third. The decline is consistent rather than confined to one category — epoch 3 is worse on overall, non-live, live, multi-turn and memory alike — which reads as mild overfitting past epoch 2 rather than noise.

Finding 01

Multi-turn is the whole story

The previous suite's central result was that multi-turn sat on the floor: across twenty ToolACE checkpoints it never cleared 3.25%, and the reasoning run never cleared 1.25%. ToolMind moves it to 16.75% — still only half the Qwen3-4B Instruct reference, but a different regime entirely from where the ToolACE runs lived.

Finding 02

Single-turn saturated in the first epoch

Non-live AST moves 81.54 → 81.38 → 80.92 and live accuracy 77.42 → 77.79 → 77.20. Flat, and marginally downward. Whatever the model learned about formatting a call and picking the right function, it had learned by the end of epoch 1; the second and third epochs bought movement only in the multi-turn and memory families.

Finding 03

The model still says nothing a quarter of the time

Counting BFCL's own Empty response from the model across every multi-turn step gives a behavioural measure that is independent of scoring: 25.8% → 25.1% → 24.5% across the three epochs, on samples of roughly ten thousand steps each.

It falls monotonically, unlike the accuracy scores, so the two are measuring different things. The model becomes slightly less likely to fall silent with more training, while its ability to drive the API to the correct final state peaks at epoch 2 and then regresses. Even at the best checkpoint, a quarter of multi-turn steps produce nothing at all.

Why an empty response is fatal to the score

Multi-turn is graded on final API state, not on the calls. A step with no parseable call ends the turn, and the next user message arrives against unchanged state — so the remainder of the task is scored against a world the model never moved.

Caveats

What these numbers do not say

  1. Not comparable to the public leaderboard. web_search was excluded — it needs a SerpAPI key. Overall Acc is 0.10·NonLive + 0.10·Live + 0.10·Irrelevance + 0.30·MultiTurn + 0.40·Agentic, and a missing category scores 0 rather than N/A. Agentic here is literally Memory / 2 (19.14 → 9.57), so every model carries up to 20 points of penalty. Within this suite the comparisons are exact.
  2. The tool docs are in the wrong shape. BFCL serialises them flat — {"name":…, "parameters":{"type":"dict"}} — while the SFT corpus used the OpenAI-wrapped form with "type":"object". That is a real train/eval shift, kept deliberately because every official Qwen3 leaderboard entry gets the same treatment. The registered -FC-nativefmt variant would quantify it; it has not been run.
  3. Reasoning is stripped from prior turns. QwenFCHandler keeps the <think> block only for assistant turns after the most recent user message and drops it from every earlier turn. This matches the first 22-checkpoint suite exactly, so the comparison against ToolACE holds.
  4. Relevance detection is a 16-case category. The 75.00 → 68.75 → 62.50 decline is two cases and then one more. Suggestive of the same overfitting the other metrics show, but far too small to carry on its own.

Method

How the run was produced

Training: 3 epochs on 162,001 ToolMind graphsyn rows, per-device batch 4 across 8×A100-80GB, LR 2e-5 cosine, sequence packing at 16,384 with assistant-only loss under chat_template_toolmind.jinja — which supervises only the final assistant turn, the one turn ToolMind reasons. 916 optimiser steps per epoch.

Evaluation: BFCL v4, 20 categories, 5,017 entries per model, vLLM backend, each category sharded to its own GPU.

bfcl generate --model qwen3-4b-sft-toolmind-{916,1832,2748}-FC \
  --test-category simple_python,simple_java,simple_javascript,multiple,parallel,
    parallel_multiple,irrelevance,live_simple,live_multiple,live_parallel,
    live_parallel_multiple,live_irrelevance,live_relevance,multi_turn_base,
    multi_turn_miss_func,multi_turn_miss_param,multi_turn_long_context,
    memory_kv,memory_vector,memory_rec_sum \
  --backend vllm --num-gpus 1 --gpu-memory-utilization 0.9 --num-threads 32

bfcl evaluate --model <all three> --test-category <same 20>
